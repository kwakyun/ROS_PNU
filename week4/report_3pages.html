DDS P2P Discovery, QoS Reliability 호환성 실증 및 Domain 격리 검증
과목: ROS 2 로봇프로그래밍

1. 실습 개요 및 목표

본 실습은 로봇 암 액추에이터가 연결된 NVIDIA Jetson과 연산·모니터링을 담당하는 PC(WSL2) 간에 ROS 2 분산 네트워크를 구성하고, DDS(Data Distribution Service) 기반 P2P 데이터 교환 및 통신 정책을 실증하는 것을 목표로 한다.

핵심 실습 목표: ① DDS Discovery 기반 분산 노드 탐색 및 네트워크 연결성(Ping, Mirrored Net, RMW) 확립 ② /dev/ttyACM0 단일 점유 기반 Topic(5Hz 스트리밍) 및 Service(최신 상태 캐싱 응답) 파이프라인 구축 ③ QoS BEST_EFFORT vs RELIABLE 정책 호환성 실증 ④ ROS_DOMAIN_ID 변경에 따른 물리 네트워크 공유 환경 내 논리적 망 분리 검증

2. 시스템 아키텍처 및 하드웨어/네트워크 구성

2.1 하드웨어 및 네트워크 계층

  • 로봇 하드웨어: PhysicAI Arm (6-DOF 매니퓰레이터)
  • 스마트 액추에이터: Feetech STS3215 스마트 버스 서보 모터 6기 (4096 ticks/rev, 1,000,000 bps Half-duplex UART)
  • 연결 포트: /dev/ttyACM0 (Jetson USB 직결)
  • 네트워크 구성: 동일 유선 서브넷 직결 (PC: 192.168.50.10, Jetson: 192.168.50.20)
  • WSL2 통신 모드: networkingMode=mirrored (호스트 NIC 공유)

2.2 데이터 통신 파이프라인

[PhysicAI Arm 6-DOF] │ USB Serial (/dev/ttyACM0, 1Mbps) ▼ [Jetson: joint_state_publisher] (5Hz 타이머 측정) │ ├──── /joint_states Topic ────────> [PC: Listener] │ (sensor_msgs/JointState) (BEST_EFFORT) ▼ [Jetson: joint_state_server] <───── Trigger ── [PC: Client] (self._latest 캐싱) ───── Response ─> (5초 대기)
안전 원칙 (Read-Only Safety Rule): 이번 실습은 모터 각도 읽기(Monitoring)에 국한함. 고수준 SDK의 토크 자동 활성화나 목표 위치 쓰기를 방지하기 위해 scservo_sdk의 ReadPos() API만을 사용하여 안전성을 확보함.

5. 핵심 심층 실증 실험 및 분석

5.1 [실험 A] QoS Reliability 호환성 실증 실험

실험 목적: DDS의 신뢰성 호환 원칙인 "Publisher 제공 신뢰성 ≥ Subscriber 요구 신뢰성" 조건을 실증함.
실험 설계: PC의 Subscriber를 RELIABLE로 실행 고정한 상태에서 Jetson Launch의 reliability 옵션을 동적으로 변경하여 패킷 수신 여부를 관측.

Publisher (Jetson) Subscriber (PC) 통신 여부 기술적 메커니즘 및 관측 결과
BEST_EFFORT RELIABLE 불가능 (차단) PC의 ros2 topic echo --qos-reliability reliable에 데이터 전혀 출력 안 됨.
발행자의 제공 수준이 구독자의 요구 수준에 미달하여 DDS 엔드포인트 매칭 거절.
RELIABLE RELIABLE 가능 (정상) Jetson을 reliability:=reliable로 재실행하자 동일 PC 창에서 즉시 관절 데이터 출력 재개.
유실 없는 신뢰성 요구 조건 충족.
BEST_EFFORT BEST_EFFORT 가능 (기본) 직접 구현한 Listener 정상 동작. 재전송 오버헤드 없이 고속 스트리밍 유지.

5.2 [실험 B] ROS_DOMAIN_ID 논리적 망 분리 실증 실험

실험 목적: 물리적으로 동일한 IP 서브넷 상에서 ROS_DOMAIN_ID를 통한 상호 간섭 차단 검증. 

# [PC: Domain ID를 31로 변경]
$ ros2 daemon stop; export ROS_DOMAIN_ID=31; ros2 daemon start
$ ros2 node list
# 결과: Jetson의 노드가 완전히 사라짐 (발견 차단)
# [PC: Domain ID를 30으로 원상 복구]
$ ros2 daemon stop; export ROS_DOMAIN_ID=30; ros2 daemon start
$ ros2 node list
# 결과: /joint_state_publisher, /joint_state_service_server 즉시 재탐색
포트 분리 원리: DDS RTPS는 도메인별 멀티캐스트 포트를 Port = 7400 + (250 × Domain_ID) + ... 공식을 통해 할당함. Domain 30(Port 14900 대역)과 Domain 31(Port 15150 대역)은 소켓 레벨에서 패킷이 수신되지 않아 완벽한 논리적 망 격리가 성립됨.

7. 핵심 기술 검증 Q&A

Q1. Publisher와 Server를 둘 다 Jetson에 두는 이유는?
A: Publisher는 USB 직결된 모터 값을 읽기 위함이며, Server는 Jetson 내부 IPC로 최신 토픽을 빠르게 캐싱하여 원격 PC 요청에 하드웨어 부하 없이 응답하기 위함임.
Q2. Trigger.Request()에 필드가 없는데 요청 객체를 보내는 이유는?
A: Service는 RPC 모델이므로 데이터가 없더라도 "원격 함수 호출"이라는 트랜잭션 신호가 전달되어야 서버가 콜백을 실행하기 때문임.
Q3. depth=10과 5 Hz의 차이는?
A: 5 Hz는 1초당 발행 빈도(시간 주기 0.2초)이며, depth=10은 KEEP_LAST 버퍼에 보관하는 최대 메시지 샘플 개수임.
Q4. BEST_EFFORT Pub과 RELIABLE Sub이 불호환인 이유는?
A: 제공 수준(Offered)이 요구 수준(Requested)에 미달하기 때문임. Sub은 재전송 보장을 요구하지만 Pub은 재전송 큐를 지원하지 않음.

8. 결론 및 5주차 연계 과제

결론: PC–Jetson 간 DDS 기반 P2P 분산 네트워크를 안정적으로 구축하고, 5 Hz 토픽 스트리밍과 최신 상태 캐싱 서비스 통신을 완벽히 검증함. QoS 호환 규칙과 Domain ID 논리적 격리 메커니즘을 실측 데이터를 통해 증명함.

5주차 연계 계획: 4주차에 확립한 안전한 상태 모니터링(Read-Only) 분산 인프라를 기반으로, 5주차에는 PC에서 목표 각도를 전송하고 Jetson이 STS3215 모터의 토크를 제어하여 로봇을 구동하는 분산 관절 위치 제어(Joint Position Control)로 확장할 예정임.
