0. 이 자료를 읽는 방법과 학습 범위
======================================================================

이번 주차의 핵심 질문은 다음과 같다.

  “Jetson에 연결된 로봇의 관절값을 다른 컴퓨터에서 어떻게 받을까?”

3주차에 한 장비에서 실행한 Topic·Service 프로그램을 두 장비로 나누고,
네트워크·DDS 환경·QoS 조건까지 맞추는 것이 4주차의 핵심이다.
이번 실습은 상태 읽기다. 로봇을 움직이는 제어 명령은 보내지 않는다.

[중복 없이 나눈 여섯 학습 영역]

  1. 시스템 구조: 누가 어디서 무엇을 하는가?
  2. 연결 기반: 서로 다른 장비가 어떻게 만나게 되는가?
  3. 통신 계약: 어떤 데이터와 전달 규칙을 사용하는가?
  4. 코드 동작: 노드 안에서 어떤 순서로 처리하는가?
  5. 배포와 실행: 파일을 어떻게 설치하고 실행하는가?
  6. 검증과 진단: 제대로 되는지 어떻게 증명하는가?

각 개념은 위의 한 영역에서 설명하고, 뒤의 실습에서는 그 개념을 적용한다.
예를 들어 QoS의 원리는 3절에서 배우고, QoS 불일치 실험은 6절에서 한다.
마지막 7~9절은 새로운 개념이 아니라 오해 점검·문제 풀이·복습이다.

1. 시스템 구조: 장비와 노드의 책임을 나누기
======================================================================

1-1. 전체 흐름

  로봇 관절/서보
       |
       | USB 시리얼: /dev/ttyACM0
       v
  [Jetson: Publisher]
       |
       | /joint_states, JointState 메시지
       +----------------------> [PC: Topic Listener]
       |
       v
  [Jetson: Service Server] <--- [PC: Service Client]
       |                       /get_joint_state 요청
       +---------------------> 성공 여부 + 저장된 관절값

핵심: 관절값을 읽는 일을 Publisher 한 곳에 모은다.
Listener와 Server는 이미 발행된 Topic을 이용한다.
Server는 요청을 받을 때 시리얼 포트를 다시 열지 않는다.

1-2. 네 노드의 역할

  Publisher / Jetson
    실제 관절값을 읽고 일정 주기로 Topic에 발행한다.

  Topic Listener / PC
    Topic이 도착할 때마다 관절값을 출력한다.

  Service Server / Jetson
    Topic의 마지막 메시지를 보관하고 요청에 응답한다.
    이 노드는 Subscriber 역할과 Service Server 역할을 함께 수행한다.

  Service Client / PC
    Service에 한 번 요청하고 응답 결과를 출력한 뒤 종료한다.

하나의 노드가 한 종류의 통신만 해야 하는 것은 아니다.
노드의 역할과 통신 객체의 종류를 구분하는 것이 중요하다.

1-3. 왜 포트는 한 노드만 사용하나?

여러 프로그램이 같은 시리얼 장치에 동시에 접근하면 요청과 응답이
섞이거나 장치 사용 충돌이 발생할 수 있다.
따라서 제조사 Bringup과 이전 실습 노드를 종료하고 Publisher만 실행한다.

“여러 곳에서 관절값을 보고 싶다”는 요구는 시리얼 연결을 늘려 해결하지 않는다.
Subscriber를 추가해 같은 Topic을 받으면 된다.

1-4. 이름 네 종류 구분하기

  패키지 이름:      week04_pc_jetson_comm
    코드를 묶고 설치하는 단위

  실행 파일 이름:  joint_state_server
    ros2 run에서 선택하는 진입점

  노드 이름:      joint_state_service_server
    실행 중 ROS 그래프에 나타나는 이름

  Service 이름:   /get_joint_state
    Client가 요청을 보내는 통신 경로

Python 파일 이름은 joint_state_service_server.py이다.
이 다섯 이름이 모두 같아야 하는 것은 아니다. setup.py가 실행 이름과
Python 모듈의 main 함수를 연결한다.

2. 연결 기반: 네트워크, DDS, 실행 환경
======================================================================

2-1. 네트워크는 “상대 장비까지 가는 길”이다

PC와 Jetson을 같은 유선 네트워크에 연결한다.
직결 예시: PC 192.168.50.10/24, Jetson 192.168.50.20/24.
이 주소는 예시다. 실제 실습실의 주소와 겹치지 않도록 설정한다.

  hostname -I
    현재 장비의 IP 주소 확인. 여러 주소가 나오면 유선 주소를 구분한다.

  ping -c 3 <Jetson_IP>
    Jetson까지 ICMP 통신이 되는지 확인한다.

  ssh <사용자명>@<Jetson_IP>
    Jetson에 원격 로그인해 명령을 실행한다.

Ping 성공은 DDS 통신 성공과 다르다.
SSH 성공도 ROS Topic 수신 성공을 보장하지 않는다.
각 명령이 확인하는 통신 경로가 다르기 때문이다.

2-2. DDS와 Discovery는 “통신 상대 찾기”를 담당한다

DDS: Data Distribution Service.
ROS 2의 기본적인 분산 통신을 뒷받침하는 미들웨어다.

Discovery: 누가 어떤 이름·타입·QoS로 통신하는지 알아내는 과정이다.
실습의 기본 구성에서는 ROS 1 Master와 같은 중앙 서버를 따로 띄우지 않는다.

두 단계를 구분하자.

  발견: 상대 노드와 통신 지점이 존재한다는 것을 앎
  전달: 실제 Topic 메시지 또는 Service 요청·응답이 오감

발견 목록에 보인다고 데이터 전달까지 성공한 것은 아니다.
QoS가 안 맞거나 Publisher가 하드웨어 읽기에 실패하면 데이터가 없을 수 있다.

2-3. 환경 변수 세 개는 서로 다른 질문에 답한다

  ROS_DOMAIN_ID=30
    “어느 논리적 통신 그룹에 참여할 것인가?”
    이번 실습에서는 PC와 Jetson을 같은 값으로 맞춘다.
    30은 실습에서 정한 값이며 IP 주소나 TCP 포트 번호가 아니다.

  ROS_LOCALHOST_ONLY=0
    “내 컴퓨터 밖과도 통신할 것인가?”
    1이면 로컬 호스트로 범위를 제한한다. 장비 간 실습에서는 0을 사용한다.

  RMW_IMPLEMENTATION=rmw_fastrtps_cpp
    “ROS 통신에 어떤 RMW 구현체를 사용할 것인가?”
    RMW는 ROS API와 통신 미들웨어 사이를 연결하는 계층이다.
    이 값은 실습에서 사용하는 Fast DDS 기반 구현체를 선택한다.

Domain이 같아도 네트워크가 막혀 있으면 통신할 수 없다.
같은 RMW로 통일하는 것은 실습의 조건을 일정하게 만드는 선택이다.
환경 변수를 설정하는 것만으로 해당 RMW 패키지가 설치되지는 않는다.

2-4. source와 export는 왜 매 터미널에서 하나?

source는 설정 스크립트를 현재 셸에 읽어 들인다.
export는 해당 셸과 그 셸에서 앞으로 시작할 자식 프로세스에 값을 전달한다.

새 터미널·새 SSH 접속은 이전 터미널의 설정을 자동으로 이어받지 않는다.
이미 실행 중인 노드도 나중에 변경한 환경 변수를 자동으로 반영하지 않는다.

따라서 실행 순서는 다음과 같다.

  ROS 기본 환경 source → 내 패키지 환경 source → export → 노드 실행

2-5. ros2 daemon은 Master가 아니다

daemon은 CLI의 그래프 조회를 돕는 백그라운드 프로세스다.
Publisher와 Subscriber의 모든 메시지를 중계하는 중앙 서버가 아니다.

Domain이나 RMW를 바꿨는데 목록이 이상하면 daemon도 이전 설정으로
실행 중인지 확인한다. 변경 전 환경에서 stop, 변경 후 환경에서 start한다.
daemon을 종료해도 이미 실행 중인 실습 노드가 함께 종료되지는 않는다.

2-6. Ubuntu와 WSL2의 차이

순수 Ubuntu PC에서는 Windows 네트워크 설정이 필요 없다.
WSL2는 Windows 안에서 Linux를 실행하므로 별도 네트워크 계층을 확인해야 한다.

자료의 WSL2 준비 사항:
  Windows 사용자 홈의 .wslconfig에 networkingMode=mirrored 설정
  wsl --shutdown 후 WSL 재시작
  관리자 PowerShell에서 실습에 맞는 Hyper-V 방화벽 설정

상세 명령과 지원 환경은 docs/troubleshooting.md의 9절을 따른다.
WSL2 사용 시 PC용 ROS 명령은 Windows PowerShell이 아니라 WSL Ubuntu에서 실행한다.

3. 통신 계약: Topic, Service, QoS
======================================================================

3-1. Topic과 Service는 사용 목적이 다르다

  Topic
    생산자가 데이터를 발행하고 구독자가 받는다.
    이번 실습: 관절값을 계속 관찰한다.
    Listener가 매번 측정 요청을 보내는 구조가 아니다.

  Service
    Client가 요청하고 Server가 응답한다.
    이번 실습: 요청한 시점에 Server가 가진 마지막 관절값을 한 번 받는다.

Topic이 반드시 주기적이어야 하거나 Service가 반드시 하드웨어를 직접
조작해야 하는 것은 아니다. 위 설명은 이번 실습에서의 사용 방식이다.

3-2. Topic 이름과 메시지 타입

  이름: /joint_states
  타입: sensor_msgs/msg/JointState

이름은 “어디로 보내는가”, 타입은 “어떤 구조로 보내는가”를 정한다.
이번 코드가 채우는 주요 필드는 다음과 같다.

  header.stamp: 메시지를 만들 때 넣는 ROS 시각
  name[]:       관절 이름 배열
  position[]:   각 이름에 대응하는 관절 위치 배열

  예: name     = [shoulder_pan, elbow_flex]
      position = [0.0, 1.5708]

같은 인덱스끼리 대응하므로 elbow_flex는 약 1.5708 rad, 즉 90도다.
현재 Publisher는 시리얼 읽기가 끝난 뒤 시각을 찍는다.
6개 관절을 완전히 같은 순간에 측정했다는 의미로 해석하지 않는다.

JointState에는 velocity와 effort 필드도 있지만 이번 코드에서는 채우지 않는다.
이 실습은 서보 회전각을 rad로 표현한다. 그리퍼 값도 회전각이며 개방 폭(m)이 아니다.

3-3. Hz와 각도 단위

  5 Hz = 1초에 5번
  주기 = 1 / 주파수 = 1 / 5 = 0.2초

  deg = rad × 180 / π
  rad = deg × π / 180

5 Hz는 Timer의 목표 설정이다. 실제 수신 속도는 서보 응답 지연·실패·
네트워크 손실·컴퓨터 부하 때문에 달라질 수 있다.

3-4. Service 이름과 타입

  이름: /get_joint_state
  타입: std_srvs/srv/Trigger

Trigger의 형식:

  [Request: 필드 없음]
  ---
  bool success
  string message

구분선 위는 요청, 아래는 응답이다.
“빈 요청”도 실제 Service 요청이다. Request 객체를 만들고 전송한다.
별도의 사용자 정의 .srv 파일은 필요하지 않다.

응답 예:
  success=True
  message="elbow_flex=+1.5708 rad (+90.00 deg)"

success=False는 Server가 실패 결과를 응답했다는 뜻일 수 있다.
응답 자체가 오지 않은 네트워크 시간 초과와 구분해야 한다.

3-5. QoS의 네 구성 요소

QoS: Quality of Service. 메시지를 보관하고 전달할 때 사용하는 정책이다.

  History
    어떤 방식으로 메시지를 보관할지 정한다. 이번 구성은 KEEP_LAST다.

  Depth
    KEEP_LAST에서 보관할 샘플 수의 제한이다. 이번 구성은 10이다.
    10 Hz라는 뜻도, 구독자 10개라는 뜻도 아니다.

  Reliability
    전달 신뢰성을 어떤 수준으로 요구·제공할지 정한다.
    이번 실습에서 직접 바꾸는 정책이다.

  Durability
    늦게 연결한 구독자에게 과거 데이터를 제공할지에 관한 정책이다.
    이번 구성은 VOLATILE이므로 연결 전 기록을 받는다고 기대하지 않는다.

3-6. BEST_EFFORT와 RELIABLE

  BEST_EFFORT
    손실된 데이터에 대해 재전송 보장을 요구하지 않는다.
    반복적으로 갱신되는 센서값에서 사용하기 좋다.
    데이터가 반드시 유실된다는 뜻은 아니다.

  RELIABLE
    전달 신뢰성을 높이기 위해 손실 복구·재전송을 수행한다.
    처리 지연이나 통신 비용이 증가할 수 있다.
    네트워크 단절까지 극복하거나 항상 더 빠르다는 뜻은 아니다.

호환성의 판단 기준은 “Publisher의 제공 수준이 Subscriber 요구를 충족하는가?”다.
아래 표는 다른 QoS 조건이 호환된다는 전제에서 Reliability만 비교한 것이다.

  Publisher       Subscriber      호환
  BEST_EFFORT     BEST_EFFORT     O
  BEST_EFFORT     RELIABLE        X
  RELIABLE        BEST_EFFORT     O
  RELIABLE        RELIABLE        O

외울 문장:
  “더 낮은 신뢰성을 제공하면서 더 높은 신뢰성 요구를 만족시킬 수는 없다.”

3-7. 이번 Launch의 reliability가 바꾸는 범위

같은 값을 받는 대상:
  Jetson Publisher의 /joint_states 발행 QoS
  Jetson Server의 /joint_states 구독 QoS

PC Listener는 BEST_EFFORT로 고정이다.
Service의 요청·응답 QoS 자체를 바꾸는 옵션으로 혼동하지 않는다.

======================================================================
4. 코드 동작: 생성, 이벤트 처리, 종료
======================================================================

4-1. ROS 노드의 공통 생애주기

  rclpy.init()
    ROS 통신 환경 초기화

  Node 생성
    Publisher·Subscription·Service·Timer 등의 통신 객체 준비

  rclpy.spin(node)
    이벤트를 기다리고 준비된 callback을 실행

  node.destroy_node(), rclpy.shutdown()
    노드 자원과 ROS 환경 정리

callback은 “이벤트가 발생했을 때 실행할 함수”다.
Timer callback, Topic 수신 callback, Service 요청 callback을 구분해서 읽는다.
spin은 데이터 값을 만드는 함수가 아니라 callback 처리가 진행되게 하는 과정이다.

4-2. Publisher: 측정 → 메시지 작성 → 발행

생성할 때:
  1) 설치된 config/joints.yaml을 읽는다.
  2) reliability 파라미터를 읽는다. 기본값은 best_effort다.
  3) create_publisher(JointState, "/joint_states", QoS)로 발행 객체를 만든다.
  4) 읽기 전용 하드웨어 연결을 준비한다.
  5) create_timer(1 / publish_hz, self._publish_state)로 Timer를 만든다.

_publish_state가 실행될 때:
  1) 모든 관절 위치를 읽는다.
  2) 실패하면 오류를 출력하고 이번 발행을 건너뛴다.
  3) JointState의 시각·이름·위치를 채운다.
  4) self._publisher.publish(message)로 발행한다.

중요: 노드가 살아 있는 것과 측정에 성공하는 것은 다르다.

4-3. hardware_interface와 joints.yaml

joints.yaml에는 통신 환경과 관절 대응 관계가 들어간다.

  device: /dev/ttyACM0
  baudrate: 1000000
  publish_hz: 5.0
  joint_names / servo_id: 관절 이름과 실제 서보 번호의 대응
  sign / zero_offset_rad: 출력 각도의 방향·영점 변환
  ticks_per_rev: 4096
  center_tick: 2048

변환식:
  rad = (tick - center_tick) × 2π / ticks_per_rev × sign + zero_offset_rad

제공 설정에서 tick 3072라면:
  (3072 - 2048) × 2π / 4096 = π/2 rad = 90도

이 값들은 실습 로봇과 대조해야 한다. 모든 STS 장비의 실제 설정을 보장하는 값은 아니다.
zero_offset_rad는 표시값의 수학적 보정이며 서보 EEPROM에 쓰는 명령이 아니다.

완성 코드의 구현 보완:
  고수준 ServoController의 자동 설정·토크 변경을 피하기 위해
  같은 SDK에 포함된 scservo_sdk의 위치 읽기 API를 사용한다.
  연결·해제는 포트를 관리하며 토크나 목표 위치를 변경하지 않는다.

4-4. Listener: 수신 이벤트 처리

create_subscription에 다음을 연결한다.
  타입 JointState / 이름 /joint_states / callback self._on_state
  QoS depth 10 / BEST_EFFORT

메시지가 도착하면 _on_state가 이름과 위치를 짝지어 rad·deg로 출력한다.
받는 노드에 별도 5 Hz Timer가 있어야 하는 것은 아니다.
현재 Listener의 출력 계기는 메시지 도착이다.

4-5. Server: 캐시 갱신과 요청 응답을 분리

캐시란 나중에 사용할 데이터를 저장해 두는 공간이다.
이번 코드의 캐시는 self._latest 한 개다.

  Topic 도착 → _on_state(message) → self._latest = message

  요청 도착 → _on_request(request, response)
            → self._latest 확인
            → 없다면 success=False
            → 있다면 format_joint_state() 결과와 success=True

완성본은 이름·위치 배열이 비거나 길이가 잘못된 메시지도 실패로 처리한다.
이는 기본 실습 요구에 추가한 입력 검증이다.

생각해 보기:
  10:00:00에 마지막 Topic을 받은 뒤 Publisher가 멈췄다.
  10:00:10에 Client가 요청하면 무엇을 받는가?

  답: Server가 살아 있으면 10:00:00에 저장한 값을 성공 응답할 수 있다.
      현재 코드는 데이터 만료 시간을 검사하지 않는다.
      “마지막 수신값”과 “방금 새로 측정한 값”은 다르다.

4-6. Client: 발견 대기와 응답 대기를 구분

  create_client(Trigger, "/get_joint_state")
    호출할 Service Client를 만든다.

  wait_for_service(timeout_sec=5.0)
    Service가 나타나는지 제한 시간 동안 기다린다.

  call_async(Trigger.Request())
    빈 요청을 한 번 보내고 Future를 받는다.

  spin_until_future_complete(..., timeout_sec=5.0)
    응답 처리가 진행되도록 하면서 완료를 기다린다.

Future는 “나중에 완료될 작업의 결과를 확인하는 객체”다.
call_async를 호출했다고 즉시 결과 데이터가 들어오는 것은 아니다.
이 Client 프로그램은 결과를 기다린 뒤 끝나지만, 요청 API 자체는 비동기다.

현재 완성본의 결과 구분:
  발견 실패 / 응답 시간 초과 / 취소·예외 / Server의 실패 응답 / 성공 응답

request_once()는 성공이면 True, 실패면 False를 반환한다.
main은 이를 프로세스 종료 코드 0 또는 1로 바꾼다.
5초씩의 제한은 완성 코드의 선택이며 ROS Service 전체의 공통 제한은 아니다.

4-7. Launch: 여러 노드의 실행 조건을 한곳에서 관리

jetson_bringup.launch.py는 두 실행 파일을 시작한다.
  joint_state_publisher
  joint_state_server

DeclareLaunchArgument로 reliability를 선언하고,
LaunchConfiguration으로 입력값을 읽어 두 노드의 parameter로 전달한다.

  reliability:=reliable

위 문법은 launch argument 전달이다. 이름이 같아도 launch argument와
노드 parameter는 서로 다른 단계이며 launch 파일이 둘을 연결한다.

현재 코드는 시작할 때 QoS 객체를 만든다.
실행 중 ros2 param set으로 문자열 값만 바꿔도 기존 QoS 객체가 자동 재생성되지는 않는다.
실습에서는 Launch를 종료하고 새 옵션으로 다시 실행한다.

5. 배포와 실행: 파일 위치부터 명령까지
======================================================================

5-1. workspace와 package

workspace: 여러 패키지를 찾고 빌드하는 작업 공간
package:   설치 정보와 소스 코드를 묶은 단위

권장 배치:

  ~/ros2_ws/
    src/
      week04_pc_jetson_comm/
        package.xml
        setup.py
        setup.cfg
        resource/week04_pc_jetson_comm
        config/joints.yaml
        launch/jetson_bringup.launch.py
        week04_pc_jetson_comm/
          __init__.py
          hardware_interface.py
          qos.py
          joint_state_topic_publisher.py
          joint_state_topic_listener.py
          joint_state_service_server.py
          joint_state_service_client.py

바깥 week04_pc_jetson_comm은 ROS 패키지 폴더,
안쪽 동명 폴더는 import할 Python 모듈 폴더다.
같은 이름의 폴더가 두 번 있다고 잘못 복사한 것은 아니다.

~는 각 장비 로그인 계정의 홈이다. PC와 Jetson의 사용자 이름은 달라도 된다.
두 장비에 같은 패키지 소스를 놓고 각각 빌드한다.

5-2. 홈에 패키지만 바로 놓는 방법도 가능한가?

가능하다. src는 권장 배치이며 이 단일 패키지를 실행하기 위한 필수 폴더는 아니다.

  ~/week04_pc_jetson_comm/package.xml

이렇게 배치했다면 패키지 폴더 자체를 빌드 기준 위치로 사용한다.

  cd ~/week04_pc_jetson_comm
  colcon build --symlink-install --packages-select week04_pc_jetson_comm
  source ~/week04_pc_jetson_comm/install/setup.bash

underlay source와 의존성 설치는 여전히 필요하다.
이후 명령의 패키지 이름·실행 이름은 같다. 빌드 위치와 overlay 경로만 달라진다.
아래 5-5절 이후 명령은 권장 배치 ~/ros2_ws 기준이므로 두 경로를 섞지 않는다.
홈 전체에서 무작정 빌드하면 다른 패키지까지 검색할 수 있어 빌드 위치를 명확히 정한다.

5-3. 설정 파일의 책임

  package.xml
    패키지 이름, 빌드 형식, ROS 실행 의존성을 선언한다.
    rclpy, sensor_msgs, std_srvs, launch, launch_ros,
    ament_index_python, python3-yaml 등이 해당한다.

  setup.py
    Python 모듈 설치와 console_scripts 진입점을 등록한다.
    data_files로 config·launch·ament 식별 파일을 설치한다.
    install_requires에 setuptools와 PyYAML을 선언한다.

  setup.cfg
    ros2 run이 찾는 패키지별 실행 파일 설치 위치를 지정한다.

  resource/week04_pc_jetson_comm
    ament 패키지 인덱스에 등록하는 식별 파일이다. 비어 있어도 필요하다.

  config/joints.yaml
    로봇 연결과 관절 변환 설정이다.
    현재 구현에서는 자체 YAML 로더로 읽으며 ros__parameters 형식이 아니다.

  launch/jetson_bringup.launch.py
    어떤 노드를 어떤 파라미터로 함께 실행할지 정한다.

5-4. 빌드 결과와 source 순서

colcon build 후에는 다음 폴더가 생성된다.
  build/:   빌드 작업 결과
  install/: 실행·검색에 사용할 설치 결과
  log/:     빌드 로그

underlay는 기존 ROS 설치 환경이고 overlay는 이번에 만든 패키지 설치 환경이다.
기본 ROS 환경을 먼저 읽고 내 패키지 환경을 나중에 읽는다.

  source <ROS 설치 위치>/setup.bash
  source <이번 빌드 위치>/install/setup.bash

--symlink-install은 가능한 파일을 링크해 개발을 편하게 한다.
모든 변경이 재빌드·재시작 없이 반영된다는 뜻은 아니다.
setup.py, 설치 데이터, 새 파일 변경은 재빌드하고 실행 중 노드도 다시 시작한다.

5-5. 준비와 빌드

전제:
  양쪽에 ROS 2 Humble과 colcon, PyYAML 등 필요한 의존성이 준비되어 있다.
  Jetson에는 완성본이 사용하는 vassar-feetech-servo-sdk 1.5.0이 필요하다.
  Jetson 사용자에게 시리얼 장치 권한이 있어야 한다.
  상세 설치는 UBUNTU_GUIDE.md의 3절을 따른다.

[PC]
  source /opt/ros/humble/setup.bash
  cd ~/ros2_ws
  colcon build --symlink-install --packages-select week04_pc_jetson_comm
  source ~/ros2_ws/install/setup.bash

[Jetson]
  source ~/ros2_base/install/setup.bash
  cd ~/ros2_ws
  colcon build --symlink-install --packages-select week04_pc_jetson_comm
  source ~/ros2_ws/install/setup.bash

Jetson도 /opt/ros/humble에 설치된 장비라면 실제 underlay 경로를 사용한다.
Windows의 build·install 폴더를 복사하지 않는다.

5-6. 새 터미널 공통 준비

각 터미널에서 먼저 해당 장비의 underlay와 이번 overlay를 source한다.
그다음 다음 값을 설정한다.

  export ROS_DOMAIN_ID=30
  export ROS_LOCALHOST_ONLY=0
  export RMW_IMPLEMENTATION=rmw_fastrtps_cpp

PC에서는 필요하면 ros2 daemon start를 실행한다.
이전 Domain/RMW로 실행한 daemon이 있으면 6절의 방식으로 먼저 정리한다.

5-7. 실제 실행

[Jetson 터미널 A: 두 노드 함께 실행]
  ros2 launch week04_pc_jetson_comm jetson_bringup.launch.py reliability:=best_effort

[PC 터미널 B: 관절값 계속 관찰]
  ros2 run week04_pc_jetson_comm joint_state_topic_listener

[PC 터미널 C: 한 번 요청]
  ros2 run week04_pc_jetson_comm joint_state_client
  echo $?

echo $?는 바로 직전 명령의 종료 코드다. 중간에 다른 명령을 넣지 않는다.
성공이면 0이다. Client가 응답 후 종료되는 것은 정상이다.
실습 종료 시 A와 B에서 Ctrl+C를 사용한다.

6. 검증과 진단: 결과를 보고 원인을 좁히기

6-1. 기본 통신 검증

  ros2 node list
    Jetson의 Publisher와 Server가 발견되는가?

  ros2 topic info /joint_states --verbose
    Publisher가 실제 존재하는가? 타입과 endpoint QoS가 맞는가?

  ros2 topic echo /joint_states sensor_msgs/msg/JointState --qos-reliability best_effort
    실제 메시지가 계속 들어오는가? 확인 후 Ctrl+C로 종료한다.

  ros2 topic hz /joint_states
    이 구독자가 받은 속도가 목표인 약 5 Hz에 가까운가?

  ros2 service list
  ros2 service type /get_joint_state
    Service 이름과 Trigger 타입이 맞는가?

  ros2 service call /get_joint_state std_srvs/srv/Trigger '{}'
    Python Client 외에 CLI로도 응답을 받는가?

practice.md의 ros2 service info는 기본 Humble CLI에 없는 명령이다.
지원 여부는 ros2 service --help로 확인하고 위 list·type·call을 사용한다.
CLI 호출에 Python Client와 동일한 5초 제한이 있다고 가정하지 않는다.

6-2. 실험 A: Reliability만 바꿔 보기

실험 질문:
  Publisher가 제공하는 신뢰성이 구독자의 요구보다 낮으면 어떻게 될까?

통제할 조건:
  PC·Jetson Domain 30, 같은 네트워크, 같은 Topic 타입
  PC의 RELIABLE echo는 실험 중 그대로 유지

[PC]
  ros2 topic echo /joint_states --qos-reliability reliable

[Jetson: 기존 Launch 종료 후]
  ros2 launch week04_pc_jetson_comm jetson_bringup.launch.py reliability:=best_effort

예상: PC RELIABLE echo는 수신하지 못한다.
이때 기본 Listener는 BEST_EFFORT이므로 수신할 수 있다.

[Jetson: 다시 Ctrl+C 후]
  ros2 launch week04_pc_jetson_comm jetson_bringup.launch.py reliability:=reliable

예상: 같은 PC echo에서 수신이 시작된다.
Service도 다시 호출해 정상 응답하는지 확인한다.
이 실험에서 미수신은 반드시 고장이 아니라 의도한 호환성 결과일 수 있다.

6-3. 실험 B: Domain만 바꿔 보기

실험 질문:
  같은 네트워크여도 서로 다른 ROS 그룹이면 발견되는가?

PC의 Listener·echo를 종료한다. Jetson은 Domain 30을 유지한다.
PC의 진단 터미널에서 순서대로 실행한다.

  ros2 daemon stop
  export ROS_DOMAIN_ID=31
  ros2 daemon start
  ros2 node list
  ros2 topic list
  ros2 service list

예상: Jetson의 노드·/joint_states·/get_joint_state가 보이지 않는다.
/rosout, /parameter_events 등 로컬 항목은 남을 수 있다.

복구:
  ros2 daemon stop
  export ROS_DOMAIN_ID=30
  ros2 daemon start
  ros2 node list
  ros2 run week04_pc_jetson_comm joint_state_client

예상: Jetson을 다시 발견하고 Service 호출도 성공한다.
PC와 Jetson을 둘 다 31로 바꾸면 불일치 실험이 성립하지 않는다.

6-4. 장애 원인을 분류하는 여섯 질문

  1) 패키지를 실행할 수 있는가?
     안 되면: 경로, 의존성, 빌드, source, 실행 이름 확인

  2) Jetson Publisher가 실제 관절값을 읽는가?
     안 되면: 포트, 권한, 중복 접근, 전원, ID, baudrate 확인

  3) PC가 Jetson까지 네트워크로 도달하는가?
     안 되면: 케이블, IP 대역, 경로, 방화벽 확인

  4) PC가 Jetson 노드를 발견하는가?
     안 되면: Domain, localhost, RMW, daemon, DDS 경로 확인

  5) 노드는 보이는데 Topic 데이터가 오는가?
     안 되면: Publisher 수, 실제 발행 여부, endpoint QoS 확인

  6) Topic은 되는데 Service가 되는가?
     안 되면: Server 생존, Service 이름·타입, 캐시, 응답 경로 확인

증상이 여러 개 겹칠 수 있다. 한 번에 여러 설정을 바꾸지 말고,
앞 단계부터 확인해 바꾼 내용과 결과를 기록한다.

자세한 증상별 명령은 docs/troubleshooting.md에서 찾는다.

7. 자주 하는 오해 바로잡기
======================================================================

  “Ping이 되면 ROS도 된다.”
    → IP 진단과 DDS 발견·데이터 전달은 별도로 확인한다.

  “Topic 이름이 보이면 데이터도 발행 중이다.”
    → Subscriber 때문에 이름이 보일 수도 있다. Publisher 수와 실제 데이터를 본다.

  “Service 요청이 오면 로봇을 새로 읽는다.”
    → 현재 Server는 Topic으로 받아 둔 마지막 값을 반환한다.

  “success=True면 현재 로봇 상태가 방금 측정됐다.”
    → 데이터 만료 검사가 없으므로 오래된 캐시일 수 있다.

  “depth=10이면 10 Hz다.”
    → depth는 보관 샘플 수, Hz는 시간당 발생 빈도다.

  “RELIABLE은 무조건 더 빠르고 모든 상황에서 손실이 없다.”
    → 신뢰성을 높이는 정책이며 지연·자원·네트워크 한계는 별도로 존재한다.

  “Server는 Service만 하고 Subscriber는 못 한다.”
    → 이 실습 Server가 바로 두 역할을 함께 수행한다.

  “Launch 하나를 실행했으니 두 노드 모두 정상이다.”
    → 한 노드만 실패할 수 있다. 각 프로세스와 데이터를 확인한다.

  “패키지를 홈에 놓으면 무조건 틀리다.”
    → 빌드 기준 위치와 overlay 경로를 맞추면 가능하다. src는 권장 구성이다.

  “한 터미널에서 export했으니 다른 터미널도 바뀐다.”
    → 각 셸과 새로 시작하는 프로세스의 환경을 따로 확인한다.

8. 확인 문제와 해설

[문제: 정답을 가리고 먼저 설명해 보기]

Q1. Publisher와 Server를 둘 다 Jetson에 두는 이유를 각각 설명하라.
Q2. Server도 시리얼 포트를 열도록 만들면 어떤 문제가 생길 수 있는가?
Q3. 5 Hz Timer의 주기는 몇 초인가? depth=10과 어떤 차이가 있는가?
Q4. /joint_states와 sensor_msgs/msg/JointState는 각각 무엇을 뜻하는가?
Q5. BEST_EFFORT Publisher와 RELIABLE Subscriber는 왜 호환되지 않는가?
Q6. RELIABLE Publisher를 BEST_EFFORT Listener로 구독하면 받을 수 있는가?
Q7. Trigger.Request()에 필드가 없다면 왜 요청 객체가 필요한가?
Q8. call_async()의 반환값은 실제 관절값인가?
Q9. Server에서 success=False 응답을 받았다. 네트워크가 완전히 끊겼다고 볼 수 있는가?
Q10. Publisher 종료 후에도 Service가 성공한다면 현재 코드에서 가능한 이유는?
Q11. PC의 새 터미널에서만 Package not found가 난다. 가장 먼저 무엇을 확인하는가?
Q12. 두 장비 모두 Domain 31로 바꿨는데 계속 통신한다. 실험 실패인가?
Q13. reliable echo는 안 되는데 기본 Listener는 된다. 가능한 조합은?
Q14. reliability 파라미터를 실행 중 바꿨는데 동작이 그대로다. 어떻게 실험해야 하는가?
Q15. 관절 하나가 읽기에 실패하면 현재 Publisher는 나머지 값만 발행하는가?
Q16. colcon build 성공만으로 실제 로봇 통신까지 검증됐다고 말할 수 있는가?

[정답과 해설]

A1. Publisher는 로봇과 직접 연결된 장비에서 읽기 위해, Server는 그 Topic을
    받아 원격 요청에 응답하기 위해 둔다. Server의 Jetson 배치는 이번 설계의 선택이다.

A2. 포트 중복 접근·요청/응답 혼선과 측정 책임 중복이 생길 수 있다.
    Publisher의 데이터를 Topic으로 공유하면 된다.

A3. 0.2초다. Hz는 발행 빈도이고 depth는 KEEP_LAST 보관 샘플 수다.

A4. /joint_states는 Topic 이름, sensor_msgs/msg/JointState는 메시지 구조의 타입이다.

A5. Publisher가 제공하는 신뢰성 수준이 Subscriber의 요구를 만족시키지 못한다.

A6. 다른 조건도 맞으면 받을 수 있다. 제공 수준이 요구를 충족한다.

A7. 데이터 필드가 없어도 Service를 호출했다는 요청은 필요하다.
    Trigger는 빈 Request와 success·message Response로 정의된다.

A8. Future다. 응답이 처리되어 완료된 뒤 결과를 확인한다.

A9. 아니다. 그 응답은 수신했으므로 요청·응답 통신이 이루어진 것이다.
    아직 캐시가 없거나 메시지가 잘못된 경우 등을 조사한다.

A10. Server가 마지막 JointState를 저장했고 이를 만료시키지 않기 때문이다.
     실제 Topic 반복 수신과 시각 갱신도 확인해야 한다.

A11. 해당 터미널에서 올바른 underlay와 overlay를 source했는지 확인한다.

A12. 아니다. 두 장비의 Domain이 같으므로 통신할 수 있다.
     불일치 검증은 Jetson 30을 유지하고 PC만 31로 바꾼다.

A13. Publisher가 BEST_EFFORT인 경우다. 실제 endpoint QoS로 확인한다.

A14. 현재 구현은 기존 QoS 객체를 다시 만들지 않는다.
     Launch를 종료하고 새로운 reliability 인자로 재실행한다.

A15. 아니다. 오류를 기록하고 해당 주기의 전체 발행을 건너뛴다.

A16. 아니다. 빌드는 설치·구성을 확인하는 단계다.
     실제 장비에서 발견, Topic 수신, Service 응답, QoS·Domain 실험을 별도로 확인한다.

9. 실습 완료 체크와 1분 복습
======================================================================

[직접 확인한 항목에 표시]

  [ ] 네 노드의 역할과 실행 장비를 설명할 수 있다.
  [ ] Topic 이름·타입·노드 이름·실행 이름을 구분한다.
  [ ] PC와 Jetson의 IP 및 SSH 연결을 확인했다.
  [ ] 두 장비에서 각각 빌드하고 올바른 환경을 source했다.
  [ ] PC Listener에서 실제 관절값의 반복 수신을 확인했다.
  [ ] Python Client와 CLI로 Trigger 응답을 확인했다.
  [ ] QoS 불일치 미수신과 복구 후 수신을 같은 echo에서 확인했다.
  [ ] Domain 불일치 미발견과 복구 후 재발견을 확인했다.
  [ ] 현재 Service 성공이 데이터 신선도를 보장하지 않음을 설명한다.
  [ ] 실습 노드를 Ctrl+C로 종료했다.

[1분 복습]

  구조: Jetson은 읽고 발행·응답, PC는 구독·요청한다.
  포트: Publisher 하나만 /dev/ttyACM0을 사용한다.
  발견: 네트워크와 DDS 환경을 맞춰 상대를 찾는다.
  환경: Domain 30 / localhost 0 / rmw_fastrtps_cpp.
  Topic: /joint_states / JointState / 기본 5 Hz.
  QoS: BEST_EFFORT 제공 → RELIABLE 요구 조합만 표에서 불호환.
  Service: /get_joint_state / Trigger / 마지막 Topic을 응답한다.
  Client: 유한 시간 대기 → 비동기 1회 호출 → 결과 출력 후 종료.
  패키지: 소스 외에도 진입점·설치 데이터·의존성 등록이 필요하다.
  실행: 장비별 빌드 → source → export → 역할별 노드 실행.
  검증: 발견·실제 수신·요청 응답을 따로 확인한다.
